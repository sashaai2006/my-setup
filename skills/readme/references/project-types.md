# Структура README по типам проектов

Используй гибкую структуру. Обязателен краткий маршрут к первому результату; остальные разделы добавляй только при наличии содержания.

## Общий порядок

1. Название.
2. Краткое описание и назначение.
3. Основные возможности или предназначение.
4. Требования.
5. Установка.
6. Быстрый старт.
7. Проверка результата.
8. Конфигурация.
9. Специфические разделы проекта.
10. Разработка и тестирование.
11. Участие в разработке и лицензия.

Объединяй короткие смежные разделы. Не повторяй одну команду в установке, быстром старте и разработке без необходимости.

## Библиотека или пакет

Приоритеты:

- поддерживаемые версии среды и зависимости;
- установка из подтверждённого источника;
- минимальный самодостаточный пример;
- основные публичные операции;
- ссылки на более полную документацию, если она существует;
- правила разработки и запуска тестов.

Не перечисляй весь API, если достаточно основного примера и ссылки на актуальную спецификацию.

## CLI

Приоритеты:

- установка и доступность команды после установки;
- `command --help` или иной реальный способ получить справку;
- базовый синтаксис;
- типовые вызовы с ожидаемым результатом;
- важные аргументы, коды выхода и ограничения, если они подтверждены;
- конфигурационные файлы и переменные окружения.

Не выдумывай имена исполняемых файлов: сверяй их с манифестом и точками входа.

## Приложение или сервис

Приоритеты:

- системные зависимости и внешние сервисы;
- установка и обязательная конфигурация;
- запуск в разработке;
- URL, сообщение, лог или health-check, подтверждающий успешный запуск;
- миграции и начальная инициализация данных;
- production-запуск только по существующей конфигурации;
- тестирование и устранение типовых неполадок.

Отделяй обязательные параметры от необязательных. Не помещай реальные production-секреты в примеры.

## HTTP API

Приоритеты:

- запуск зависимостей и сервиса;
- базовый URL и проверка доступности;
- аутентификация, если требуется;
- один или несколько воспроизводимых запросов;
- ссылка на OpenAPI или иную актуальную спецификацию;
- ограничения, миграции и эксплуатационные особенности при необходимости.

Не превращай README в полную спецификацию API.

## Монорепозиторий

Приоритеты:

- назначение репозитория и карта основных компонентов;
- общие требования и установка;
- запуск типового сценария;
- команды для отдельных компонентов;
- ссылки на существующие README пакетов;
- общие проверки и правила разработки.

Документируй в корне только общее. Детали компонентов оставляй в их собственных документах.

## Учебный проект или эксперимент

Приоритеты:

- цель и границы проекта;
- требования и источник данных;
- воспроизведение основного результата;
- структура каталогов;
- команды эксперимента или анализа;
- известные ограничения.

Не представляй учебный пример production-ready без подтверждения.

## Минимальный проект

Если проект мал, достаточно названия, описания, требований, установки или запуска, примера и лицензии при наличии. Не раздувай документ разделами об архитектуре, развёртывании и участии без реальной пользы.
